# 校园食堂菜品评价系统前端开发文档

- **文档版本**：v1.0
- **编写日期**：2026-11-12
- **适用项目**：RestaurantDishes
- **关联文档**：《校园食堂菜品评价系统-接口文档》v1.2、《校园食堂菜品评价系统-数据库设计文档》v1.1
- **后端地址**：开发环境 `http://localhost:8080/api`
- **前端定位**：校园师生浏览菜品、发表与管理个人评价，管理员维护菜品并处理不当评价

> 本仓库当前是 Spring Boot 后端工程，尚未包含前端代码。本文是新建前端工程的设计与实施基线，技术栈和目录结构为推荐方案，不表示相关依赖已经安装。

## 1. 建设目标与范围

### 1.1 建设目标

1. 提供清晰、易用的菜品浏览、搜索、筛选、排序和热门排行页面。
2. 打通注册、登录、退出及 JWT 鉴权流程，正确区分未登录与无权限。
3. 支持用户发表、修改、删除自己的评价，并集中查看“我的评价”。
4. 为管理员提供菜品新增、编辑、上架、下架及评价删除能力。
5. 统一处理加载、空数据、参数错误、请求失败和重复提交等状态。
6. 同时适配桌面端和移动端，满足基本的键盘操作与可访问性要求。

### 1.2 功能边界

本期只实现后端已有或接口文档明确规划的功能，不在前端虚构以下能力：

- 不提供图片文件上传，菜品图片通过 `imageUrl` 外部地址设置。
- 不提供用户资料修改、修改密码、找回密码和账号管理。
- 不提供评价回复、点赞、举报、收藏、订单或支付功能。
- 不提供独立食堂、窗口、分类管理页面。
- 不提供物理删除菜品；管理端“删除”语义统一为“下架”。
- 不在前端计算或维护热门榜分数，直接展示后端返回顺序。

### 1.3 当前接口可联调状态

完整设计以接口文档中的 16 个接口为目标。截至本文编写时，控制器代码已实现 11 个接口，以下 5 个接口尚待后端实现：

- `GET /api/auth/me`
- `GET /api/admin/dishes`
- `POST /api/admin/dishes`
- `PUT /api/admin/dishes/{id}`
- `DELETE /api/admin/dishes/{id}`

因此，用户端主要流程可以先联调；登录状态主动校验和管理端页面应等对应接口就绪后联调。前端验收以实际部署的后端版本为准，不能仅凭接口文档判定接口可用。

## 2. 用户角色与核心流程

### 2.1 角色能力

| 功能 | 游客 | 普通用户 `USER` | 管理员 `ADMIN` |
|---|---|---|---|
| 浏览菜品、热门榜、菜品详情和评价 | 可以 | 可以 | 可以 |
| 注册、登录 | 可以 | 已登录时通常跳转首页 | 同普通用户 |
| 发表评价 | 引导登录 | 可以 | 可以 |
| 修改评价 | 不可以 | 仅自己的评价 | 仅自己的评价 |
| 删除评价 | 不可以 | 仅自己的评价 | 任意评价 |
| 查看“我的评价” | 引导登录 | 可以 | 可以 |
| 菜品管理 | 不可以 | 不可以 | 可以 |

前端通过 `role` 控制入口和路由，但这只改善使用体验，真正的权限校验仍由后端完成。不得根据前端传入的用户 ID 判断作者身份，后端应从当前登录令牌获取用户身份。

### 2.2 核心业务流程

**浏览与搜索**

```text
首页/菜品列表 → 输入关键词或选择筛选条件 → 查询菜品 → 查看详情 → 分页查看评价
```

**发表评价**

```text
菜品详情 → 点击“发表评价” → 未登录则跳转登录 → 填写评分和内容
→ 提交 → 刷新菜品统计和评价列表 → 展示新评价
```

**登录后返回原页面**

```text
受保护操作 → /login?redirect=<原页面完整路径> → 登录成功 → 返回原页面
```

`redirect` 只允许站内路径，避免把用户跳转到外部地址。

**管理菜品**

```text
管理员登录 → 菜品管理 → 搜索/筛选 → 新增或编辑 → 保存并刷新列表
→ 需要时下架；已下架菜品通过编辑完整信息并将 status 改为 1 重新上架
```

## 4. 信息架构与路由设计

### 4.1 页面路由

| 路径 | 页面 | 权限 | 说明 |
|---|---|---|---|
| `/` | 首页 | 公开 | 热门菜品、最新推荐、搜索入口 |
| `/dishes` | 菜品列表 | 公开 | 搜索、筛选、排序和分页 |
| `/dishes/:id` | 菜品详情 | 公开 | 菜品信息、评价列表、发表评价 |
| `/login` | 登录 | 公开 | 登录后返回 `redirect` 或首页 |
| `/register` | 注册 | 公开 | 注册成功后跳转登录 |
| `/me/reviews` | 我的评价 | 登录 | 修改、删除和分页查询 |
| `/admin/dishes` | 菜品管理 | `ADMIN` | 查询、新增、编辑、上下架 |
| `/403` | 无权限 | 公开 | 提供返回首页入口 |
| `/:pathMatch(.*)*` | 页面不存在 | 公开 | 404 页面 |

### 4.2 路由元信息

```ts
interface RouteMeta {
  title?: string
  requiresAuth?: boolean
  roles?: Array<'USER' | 'ADMIN'>
  guestOnly?: boolean
}
```

路由守卫规则：

1. `requiresAuth = true` 且本地无令牌：跳转登录页，并记录原页面完整路径。
2. `roles` 存在且当前角色不匹配：跳转 `/403`，不能将其当作未登录处理。
3. 已登录用户访问 `guestOnly` 页面：跳转首页。
4. 每次导航后更新 `document.title`，格式为“页面名 - 校园食堂菜品评价”。
5. 前端守卫只依赖本地状态做初步判断；接口返回 `401` 时仍须重新清理登录状态。

### 4.3 布局与导航

**用户布局 `UserLayout`**

- 顶部：系统名称、首页、菜品列表、热门榜锚点或首页入口。
- 游客右侧：登录、注册。
- 登录用户右侧：昵称、我的评价、退出登录；管理员额外显示“菜品管理”。
- 移动端：折叠导航菜单，主内容保持单列。

**管理布局 `AdminLayout`**

- 保留返回用户端的入口。
- 当前仅有“菜品管理”，不为了视觉完整而添加未实现的仪表盘或账号管理菜单。
- 表格区域允许横向滚动，操作列在桌面端固定，移动端改用卡片列表。

## 5. 页面与交互详细设计

### 5.1 通用页面状态

每个异步页面必须分别处理以下状态，不能用空白页面代替：

| 状态 | 展示要求 |
|---|---|
| 首次加载 | 使用骨架屏或加载指示，保留页面基本布局 |
| 成功有数据 | 正常展示内容 |
| 成功无数据 | 显示明确空状态和下一步操作 |
| 请求失败 | 显示错误提示和“重新加载”按钮 |
| 局部刷新 | 保留旧内容并显示局部加载，避免整页闪烁 |
| 提交中 | 提交按钮禁用并显示进度，防止重复请求 |

### 5.2 首页

**内容结构**

1. 顶部主视觉：系统简介和“搜索菜品”输入框。
2. 热门菜品：调用 `GET /dishes/hot?limit=6`，按接口返回顺序显示排名。
3. 最新菜品：调用 `GET /dishes?page=1&size=8&sort=newest`。
4. 底部入口：查看全部菜品。

**交互规则**

- 搜索提交后跳转 `/dishes?keyword=<关键词>`。
- 热门榜前三名显示排名标识，其余保留序号即可。
- 热门榜包含零评价菜品，前端不得自行过滤。
- 空榜显示“暂无菜品”，不要显示为接口错误。
- 点击菜品卡片进入对应详情页。

### 5.3 菜品列表

**筛选项**

| 控件 | 参数 | 规则 |
|---|---|---|
| 关键词输入框 | `keyword` | 最多 50 字，去首尾空格，空字符串不传递 |
| 食堂选择 | `canteenName` | 精确匹配，可清空 |
| 分类选择 | `category` | 精确匹配，可清空 |
| 排序选择 | `sort` | `newest`、`rating`、`reviewCount` |
| 分页 | `page`、`size` | 页码从 1 开始，`size` 不超过 50 |

**交互规则**

- 查询条件同步到 URL Query，刷新、分享和浏览器前进/后退后仍可恢复。
- 关键词输入可采用 300 ms 防抖，也可显式点击“搜索”；筛选和排序变化后立即查询。
- 任一筛选条件变化时将 `page` 重置为 1，避免停留在不存在的新结果页。
- 提供“重置”按钮，恢复 `page=1&size=10&sort=newest`。
- 请求只传有值的筛选参数，由 Axios 负责 URL 编码。
- 列表刷新期间禁用重复筛选请求；新查询发起时取消或忽略旧请求，防止旧响应覆盖新结果。

**卡片信息**

- 菜品图片；无图或加载失败时使用本地默认图。
- 名称、食堂、窗口、分类。
- 价格统一显示为 `¥12.00`。
- `avgRating > 0` 时显示一位小数；为 0 时显示“暂无评分”。
- 评价数显示为“18 条评价”，为 0 时显示“暂无评价”或“0 条评价”，全站保持一致。

**筛选项来源约束**

当前没有食堂或分类字典接口。第一阶段可使用与后端约定的本地配置项，或允许用户输入精确值；不要只从当前分页结果提取选项并声称其包含全部数据。后续若增加字典接口，再替换本地配置。

### 5.4 菜品详情

**页面区域**

1. 返回列表。
2. 菜品主图、名称、价格、食堂、窗口、分类、评分和评价数。
3. 菜品介绍；`description` 为空时显示“暂无菜品介绍”。
4. 评价操作区：“发表评价”按钮。
5. 评价列表与分页。

进入页面后并行请求菜品详情和第一页评价。详情或评价任一失败时，只替换对应区域，并提供独立重试。

**评价操作权限**

- 游客点击“发表评价”：跳转登录，登录成功后返回当前详情。
- 当前用户是评价作者：显示“编辑”和“删除”。
- 管理员可以删除任意评价，但不能编辑他人评价。
- 普通用户不能编辑或删除他人评价。
- 按钮隐藏不是权限边界，后端仍可能返回 `403`，前端按统一规则提示。

**新增评价**

- 表单字段为 `rating` 和 `content`，不发送 `userId`、`nickname` 等字段。
- 评分为 1～5 的整数，必选。
- 内容去首尾空格后为 2～500 字，展示字数统计。
- 提交期间禁止重复提交。
- 成功后关闭弹窗、提示“评价成功”，重新请求菜品详情，并将评价列表切回第一页。
- 返回 `409` 时展示后端“你已经评价过该菜品，可以修改原评价”，提供“前往我的评价”入口。
- 不能只根据当前评价页中是否出现当前用户来决定是否允许发表，因为用户的评价可能位于其他分页。

**编辑与删除**

- 编辑弹窗打开时回填评分和内容，调用 `PUT /reviews/{id}`。
- 修改成功后刷新详情统计和当前评价页，不额外增加评价数。
- 删除前二次确认，文案明确“删除后不可恢复”。
- 删除成功后刷新详情统计、当前评价页和“我的评价”相关缓存。

**异常场景**

菜品不存在或已下架时显示“菜品不存在或已下架”，提供返回菜品列表按钮。评价删除后若当前页已空且 `page > 1`，回退一页查询。

### 5.5 登录

**字段**

| 字段 | 校验 | 控件要求 |
|---|---|---|
| `username` | 必填 | 自动聚焦，支持 Enter 提交 |
| `password` | 必填 | 密码框，可切换可见性 |

**流程**

1. 提交 `POST /auth/login`。
2. 成功后保存 `token`、`expiresIn` 和 `userInfo`。
3. 更新 Pinia 登录状态。
4. 跳转安全的站内 `redirect`，没有时进入首页；管理员也可从首页进入管理页。
5. 登录失败保留用户名，清空密码或保持密码由统一产品规则决定，建议清空密码。

“用户名或密码错误”直接使用后端提示；账号禁用返回 `403` 时显示“账号已被禁用”，不要执行全局登出跳转覆盖该提示。

### 5.6 注册

字段包括用户名、密码、确认密码和昵称。`confirmPassword` 仅用于前端校验，不放入请求体。

| 字段 | 前端校验 |
|---|---|
| `username` | 去首尾空格，4～20 位字母、数字或下划线 |
| `password` | 6～20 个字符 |
| `confirmPassword` | 与密码一致 |
| `nickname` | 去首尾空格，1～20 个字符 |

注册成功后提示“注册成功”，跳转登录页并回填用户名。用户名重复返回 `409` 时，在用户名附近显示后端提示；前端校验不能替代后端校验。

### 5.7 我的评价

- 调用 `GET /users/me/reviews`，默认 `page=1&size=10`。
- 每条展示菜品名称、食堂、评分、内容、创建时间和更新时间。
- `updatedAt` 晚于 `createdAt` 时可显示“已编辑”。
- 支持编辑自己的评价和删除评价，复用评价表单组件。
- 点击菜品名称进入详情；已下架菜品仍出现在本页，因此进入详情可能返回 404，应按详情页下架状态处理，不能直接把历史评价隐藏。
- 空状态显示“你还没有发表评价”，提供“去逛逛菜品”按钮。

### 5.8 管理员菜品管理

> 本页等待 `/admin/**` 接口实现后联调。

**查询区域**

- 关键词、食堂、分类、状态（全部/已上架/已下架）。
- 默认 `page=1&size=10`，不包含 `sort` 参数，后端按创建时间和 ID 倒序。
- 条件变化重置页码，规则与用户列表一致。

**表格列**

菜品、食堂/窗口、分类、价格、平均评分、评价数、状态、更新时间、操作。图片可使用缩略图，描述放入编辑表单而不挤占表格。

**新增与编辑**

- 新增调用 `POST /admin/dishes`，编辑调用 `PUT /admin/dishes/{id}`。
- 编辑是全量更新，弹窗必须回填并提交所有菜品字段，不能只提交被修改字段。
- 新增时 `status` 默认 1；编辑时可改为 0 下架或改为 1 重新上架。
- 保存成功后关闭弹窗、刷新当前列表；新增成功可回到第一页查看新记录。

**下架**

- 操作名称统一为“下架”，调用 `DELETE /admin/dishes/{id}`。
- 确认文案：“下架后用户端将不再展示该菜品，历史评价会保留。确认下架？”
- 重复下架返回 `409` 时提示后端信息并刷新列表，以服务器状态为准。
- 不提供“永久删除”按钮。

### 5.9 菜品表单校验

| 字段 | 必填 | 前端规则 |
|---|---|---|
| `name` | 是 | 去首尾空格后 1～50 字 |
| `canteenName` | 是 | 去首尾空格后 1～30 字 |
| `windowName` | 是 | 去首尾空格后 1～50 字 |
| `category` | 是 | 去首尾空格后 1～20 字 |
| `price` | 是 | 0～999999.99，最多两位小数 |
| `description` | 否 | 最多 500 字，空值传空字符串 |
| `imageUrl` | 否 | 最多 255 字，校验合理的 HTTP/HTTPS URL，空值传空字符串 |
| `status` | 否 | 仅允许 0 或 1，新增默认 1 |

价格提交为 JSON number，不发送带 `¥` 的字符串；展示时再格式化为两位小数。

## 9. 请求封装与环境配置

### 9.1 开发代理

`.env.development`：

```dotenv
VITE_API_BASE_URL=/api
```

`vite.config.ts` 示例：

```ts
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()],
  server: {
    port: 5173,
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true,
      },
    },
  },
})
```

不要配置重写掉 `/api`，因为后端控制器本身以 `/api` 为前缀。生产环境优先由同源反向代理转发 `/api`；若前后端分离部署，再通过 `VITE_API_BASE_URL` 配置完整后端地址，并由后端明确配置 CORS。

### 9.2 Axios 实例

```ts
import axios from 'axios'

const request = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL || '/api',
  timeout: 10000,
  headers: {
    'Content-Type': 'application/json',
  },
})

request.interceptors.request.use((config) => {
  const token = localStorage.getItem('canteen:token')
  if (token) {
    config.headers.Authorization = `Bearer ${token}`
  }
  return config
})
```

实际实现还应做到：

1. 成功时确认 HTTP 请求成功且业务 `code === 0`，返回 `data`。
2. HTTP 成功但 `code !== 0` 时按业务失败处理，不能误判为成功。
3. 网络超时、断网和非 JSON 响应提供可理解的通用提示。
4. 请求取消不弹错误消息。
5. `401` 清理令牌和用户信息，避免重复弹窗，再跳转登录并保留当前路径。
6. `403` 只提示无权限，不自动退出；已确认角色越界访问管理页时可进入 `/403`。
7. `400`、`404`、`409` 默认展示后端 `message`；详情等页面可将其转为局部状态。
8. `500` 显示“服务器暂时异常，请稍后重试”，记录必要的调试上下文但不暴露堆栈给用户。

### 9.3 错误处理表

| HTTP/code | 前端动作 |
|---|---|
| 400 | 表单附近或消息框展示后端校验信息，保留已填内容 |
| 401 | 清理本地登录状态，跳转登录，记录原页面 |
| 403 | 展示“没有操作权限”或后端明确提示，不清空登录状态 |
| 404 | 列表/详情显示对应空态或不存在页面；操作失败时提示并刷新 |
| 409 | 展示冲突原因，如重复评价、用户名重复、菜品已下架 |
| 500 | 通用异常提示和重试入口 |
| 超时/断网 | 提示检查网络，保留表单输入 |

## 10. 登录状态管理

### 10.1 Auth Store

Pinia `auth` Store 至少包含：

```ts
interface AuthState {
  token: string
  userInfo: UserInfo | null
  initialized: boolean
}
```

建议提供以下方法：

- `login(payload)`：调用登录接口并持久化登录结果。
- `fetchCurrentUser()`：调用 `/auth/me`，接口就绪后用于刷新页面时校验会话。
- `logout()`：先请求后端退出，再清理本地状态并跳转。
- `clearLocalSession()`：统一清理令牌和用户信息，不循环调用退出接口。
- `hasRole(role)`：用于路由和按钮权限显示。

计算属性包括 `isLoggedIn`、`isAdmin`。角色信息以 `/auth/login` 或 `/auth/me` 返回的 `userInfo.role` 为准，不自行解析后信任客户端修改过的角色数据。

### 10.2 本地持久化

建议键名：

```text
canteen:token
canteen:user
```

- 第一阶段可使用 `localStorage` 保持刷新后的登录状态；不得存储密码。
- JWT 有效期为 2 小时，但前端不能只依赖本地计时判断有效性，Redis 会话被删除后同样会失效。
- `/auth/me` 尚未实现时，应用初始化可读取本地用户信息，并通过后续受保护接口的 `401` 发现失效；不要调用不存在的接口导致每次启动都报错。
- `/auth/me` 就绪后，应用初始化应校验会话并刷新用户信息，失败时按 `401` 清理。
- 退出接口网络失败时仍清理本地状态，提示“已退出本地登录”，避免旧令牌继续自动附加到请求中。
- 多标签页可监听 `storage` 事件同步退出状态。

`localStorage` 中的令牌可能被 XSS 读取，因此必须严格避免渲染未转义 HTML，并保持依赖更新。若后续改为 Cookie 会话，需要重新设计 CSRF 防护，不能只替换存储位置。

## 12. 安全、性能与可靠性

### 12.1 安全要求

1. 所有受保护请求统一由拦截器添加 `Authorization: Bearer <token>`。
2. 不记录或打印密码、完整 JWT；日志中只保留必要的接口和状态信息。
3. 评价、昵称、介绍等用户或外部数据默认按纯文本渲染，禁止直接使用 `v-html`。
4. 路由角色控制只负责展示，不能代替后端鉴权。
5. 登录回跳只接受站内路径，拒绝 `//evil.example` 或外部绝对 URL。
6. 外部菜品图可能带来隐私和混合内容风险；生产环境使用 HTTPS，并评估图片来源策略。
7. `.env` 文件只保存公开接口地址等前端配置，不能放服务端密钥；`VITE_` 变量会进入浏览器产物。

### 12.2 性能要求

- 路由页面按需加载，管理端与用户端分包。
- 菜品图片使用懒加载和尺寸占位；不加载无必要的大图。
- 搜索防抖，避免每次按键立即请求。
- 只全局保存认证状态，列表筛选和分页优先保存在页面状态与 URL 中。
- 新增、修改、删除评价后精准刷新详情和相关评价列表，不重复请求无关接口。
- 避免同时显示多个全局全屏加载遮罩，局部操作使用局部加载。

### 12.3 数据一致性

- 所有写操作以服务器结果为准，不使用未确认成功的本地假数据。
- 下架后刷新管理列表；用户端已打开的详情再次请求时可能得到 404，应正常处理。
- 删除当前页最后一条评价后调整页码。
- 弹窗表单提交失败时保留用户输入。
- 页面返回时不盲目复用旧的评分和评价数，必要时重新获取详情。
