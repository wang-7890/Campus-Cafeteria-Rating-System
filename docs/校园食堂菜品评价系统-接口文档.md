# 校园食堂菜品评价系统接口文档

- **文档版本**：v1.2
- **编写日期**：2026-11-06
- **后端基础地址**：`http://localhost:8080/api`
- **数据格式**：JSON（UTF-8）
- **认证方式**：JWT + Redis Session（登录状态白名单）
- **接口数量**：16 个

---

## 1. 通用约定

### 1.1 请求格式

除特别说明外，POST、PUT 请求均应携带：

```http
Content-Type: application/json
```

GET 请求参数通过 Query String 传递。

### 1.2 登录认证

本系统使用 **JWT（JSON Web Token）**作为登录令牌，并通过 Redis 保存有效登录状态。

需要登录的接口必须携带以下请求头：

```http
Authorization: Bearer <token>
```

其中：

- `Bearer` 是 HTTP 认证方案，表示“请求方携带了一个访问令牌”。
- `<token>` 是占位符，实际请求时替换成登录接口返回的完整 JWT，**不保留尖括号**。
- `Bearer` 与 JWT 之间必须有一个英文空格。
- `Bearer` 不是 JWT 的内容，JWT 本身也不需要以 `Bearer` 开头。

实际请求示例（以下 JWT 仅为格式示例）：

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxIiwicm9sZSI6IlVTRVIiLCJqdGkiOiJzZXNzaW9uLTAwMSJ9.example-signature
```

JWT 由 `Header.Payload.Signature` 三部分组成。本系统的 Payload 包含以下字段：

| 字段 | 说明 |
|---|---|
| sub | 用户 ID |
| role | 用户角色 |
| jti | 本次登录的唯一会话 ID |
| iat | 签发时间 |
| exp | 过期时间 |

JWT 的有效期为 2 小时。登录时，后端同时写入 Redis：

```text
Key：canteen:session:{jti}
Value：用户 ID、角色等会话信息
TTL：2 小时，与 JWT 过期时间一致
```

后端处理受保护接口时，同时检查：

1. JWT 签名是否正确、是否过期。
2. JWT 中的 `jti` 对应的 Redis Session 是否存在。

退出登录时删除对应 Redis Session。因此，即使 JWT 尚未到期，退出后也不能继续访问受保护接口。

**注意：JWT Payload 默认只是编码，不是加密，不能放入密码、密钥等敏感信息。**

### 1.3 接口权限

| 接口类型 | 访问权限 |
|---|---|
| 注册、登录 | 公开 |
| 菜品列表、热门菜品、菜品详情、菜品评价列表 | 公开 |
| 退出登录、当前用户信息、发表评价、我的评价 | 登录用户 |
| 修改评价 | 评价作者 |
| 删除评价 | 评价作者或管理员 |
| `/admin/**` | 管理员 |

### 1.4 统一响应结构

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

字段说明：

| 字段 | 类型 | 说明 |
|---|---|---|
| code | number | 业务状态码，0 表示成功 |
| message | string | 提示信息 |
| data | any | 返回数据，无数据时为 `null` |

### 1.5 通用错误码

| HTTP 状态码 | code | 含义 |
|---|---:|---|
| 200 | 0 | 请求成功 |
| 400 | 400 | 参数错误或参数校验失败 |
| 401 | 401 | 未登录、Token 无效或已过期 |
| 403 | 403 | 已登录，但没有操作权限 |
| 404 | 404 | 请求的数据不存在 |
| 409 | 409 | 数据冲突，如用户名重复、重复评价 |
| 500 | 500 | 服务器内部错误 |

错误响应示例：

```json
{
  "code": 409,
  "message": "你已经评价过该菜品，可以修改原评价",
  "data": null
}
```

参数校验失败示例：

```json
{
  "code": 400,
  "message": "rating: 评分必须为1～5的整数",
  "data": null
}
```

### 1.6 通用分页结构

```json
{
  "list": [],
  "page": 1,
  "size": 10,
  "total": 0,
  "pages": 0
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| list | array | 当前页数据 |
| page | number | 当前页码，从 1 开始 |
| size | number | 每页数量 |
| total | number | 数据总条数 |
| pages | number | 总页数 |

通用分页参数：

| 参数 | 必填 | 默认值 | 说明 |
|---|---|---|---|
| page | 否 | 1 | 页码，必须大于等于 1 |
| size | 否 | 10 | 每页数量，范围为 1～50 |

### 1.7 通用时间格式

```text
yyyy-MM-dd HH:mm:ss
```

例如：`2026-11-05 12:30:00`。

## 3. 用户认证接口

### 3.1 用户注册

- **请求方法**：POST
- **请求路径**：`/auth/register`
- **访问权限**：公开
- **完整地址**：`POST http://localhost:8080/api/auth/register`

#### 请求体

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| username | string | 是 | 4～20 位字母、数字或下划线 |
| password | string | 是 | 6～20 个字符 |
| nickname | string | 是 | 1～20 个字符，去除首尾空格后不能为空 |

#### 请求示例

```json
{
  "username": "student01",
  "password": "123456",
  "nickname": "小食同学"
}
```

#### 成功响应

```json
{
  "code": 0,
  "message": "注册成功",
  "data": null
}
```

#### 业务规则

- 用户名不区分前后空格，保存前去除首尾空格。
- 用户名必须唯一，重复时返回 `409`。
- 密码使用 BCrypt 加密后保存。
- 注册成功的角色固定为 `USER`，状态默认为正常。

---

### 3.2 用户登录

- **请求方法**：POST
- **请求路径**：`/auth/login`
- **访问权限**：公开

#### 请求体

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| username | string | 是 | 登录用户名 |
| password | string | 是 | 登录密码 |

#### 请求示例

```json
{
  "username": "student01",
  "password": "123456"
}
```

#### 成功响应

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxIiwicm9sZSI6IlVTRVIiLCJqdGkiOiJzZXNzaW9uLTAwMSJ9.example-signature",
    "tokenType": "Bearer",
    "expiresIn": 7200,
    "userInfo": {
      "id": 1,
      "username": "student01",
      "nickname": "小食同学",
      "role": "USER"
    }
  }
}
```

#### 失败场景

| 场景 | HTTP/code | message 示例 |
|---|---|---|
| 用户不存在或密码错误 | 400 | 用户名或密码错误 |
| 用户已被禁用 | 403 | 账号已被禁用 |

为避免暴露账号状态，用户不存在和密码错误使用相同的提示。

---

### 3.3 退出登录

- **请求方法**：POST
- **请求路径**：`/auth/logout`
- **访问权限**：登录用户
- **请求体**：无

#### 成功响应

```json
{
  "code": 0,
  "message": "退出成功",
  "data": null
}
```

#### 业务规则

后端从当前 JWT 中取得 `jti`，删除 Redis 中对应的 Session。退出后，即使 JWT 尚未过期，再次使用该 JWT 请求受保护接口也应返回 `401`。

## 4. 菜品公开接口

### 4.1 分页查询菜品

- **请求方法**：GET
- **请求路径**：`/dishes`
- **访问权限**：公开
- **数据范围**：只返回已上架菜品

#### Query 参数

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| page | number | 否 | 1 | 页码 |
| size | number | 否 | 10 | 每页数量，最大 50 |
| keyword | string | 否 | 无 | 按菜品名称模糊搜索，最大 50 字 |
| canteenName | string | 否 | 无 | 按食堂名称精确筛选 |
| category | string | 否 | 无 | 按分类精确筛选 |
| sort | string | 否 | newest | 排序方式，见下表 |

排序方式：

| 值 | 说明 |
|---|---|
| newest | 按创建时间倒序；创建时间相同时按菜品 ID 倒序 |
| rating | 平均评分降序；评分相同时按评价数量降序，再按菜品 ID 倒序 |
| reviewCount | 评价数量降序；数量相同时按平均评分降序，再按菜品 ID 倒序 |

#### 请求示例

```http
GET /api/dishes?page=1&size=10&keyword=番茄&canteenName=第一食堂&category=面食&sort=rating
```

#### 成功响应

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "list": [
      {
        "id": 1,
        "name": "番茄鸡蛋面",
        "canteenName": "第一食堂",
        "windowName": "3号窗口",
        "category": "面食",
        "price": 12.00,
        "imageUrl": "https://example.com/noodle.jpg",
        "avgRating": 4.5,
        "reviewCount": 18
      }
    ],
    "page": 1,
    "size": 10,
    "total": 1,
    "pages": 1
  }
}
```

## 5. 评价接口

### 5.1 发表评价

- **请求方法**：POST
- **请求路径**：`/dishes/{id}/reviews`
- **访问权限**：登录用户

#### Path 参数

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| id | number | 是 | 菜品 ID，正整数 |

#### 请求体

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| rating | number | 是 | 评分，必须为 1～5 的整数 |
| content | string | 是 | 评价内容，去除首尾空格后为 2～500 个字符 |

#### 请求示例

```http
POST /api/dishes/1/reviews
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxIiwicm9sZSI6IlVTRVIiLCJqdGkiOiJzZXNzaW9uLTAwMSJ9.example-signature
Content-Type: application/json
```

```json
{
  "rating": 5,
  "content": "份量很足，味道也不错。"
}
```

#### 成功响应

```json
{
  "code": 0,
  "message": "评价成功",
  "data": {
    "reviewId": 8
  }
}
```

#### 业务规则

- 每位用户对同一菜品只能发表一条评价。
- 数据库通过 `(dish_id, user_id)` 唯一索引保证不重复。
- 不能评价不存在或已下架的菜品。
- 新增成功后更新菜品评价统计，清除对应菜品详情缓存。
- 菜品上架状态下，根据最新 `review_count` 和 `avg_rating` 重新计算热门榜 score，并通过 `ZADD` 覆盖写入；**不要直接对原 score 加 1**。

#### 失败场景

| 场景 | HTTP/code | message 示例 |
|---|---|---|
| 未登录 | 401 | 请先登录 |
| 评分或内容不符合要求 | 400 | 参数校验失败提示 |
| 菜品不存在或已下架 | 404 | 菜品不存在或已下架 |
| 重复评价 | 409 | 你已经评价过该菜品，可以修改原评价 |

### 5.2 修改评价

- **请求方法**：PUT
- **请求路径**：`/reviews/{id}`
- **访问权限**：评价作者

#### Path 参数

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| id | number | 是 | 评价 ID，正整数 |

#### 请求体

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| rating | number | 是 | 新评分，1～5 的整数 |
| content | string | 是 | 新评价内容，2～500 个字符 |

#### 请求示例

```json
{
  "rating": 4,
  "content": "今天再次尝试，整体不错，但排队时间有点长。"
}
```

#### 成功响应

```json
{
  "code": 0,
  "message": "修改成功",
  "data": null
}
```

#### 业务规则

- 只能修改自己的评价，管理员也不能通过此接口代替用户修改。
- 修改评分后重新计算平均评分，并清除对应菜品详情缓存。
- 修改评价不会改变评价数量，但可能改变热门榜 score 的评分部分：菜品上架时根据最新统计重新计算并 `ZADD`；菜品下架时保持不入榜，不得通过本次操作重新 `ZADD`。
- 菜品已下架不影响作者修改自己的历史评价。

#### 失败场景

| 场景 | HTTP/code |
|---|---|
| 评价不存在 | 404 |
| 尝试修改他人评价 | 403 |
| 参数校验失败 | 400 |
| 未登录 | 401 |

---

### 5.3 删除评价

- **请求方法**：DELETE
- **请求路径**：`/reviews/{id}`
- **访问权限**：评价作者或管理员
- **请求体**：无

#### 成功响应

```json
{
  "code": 0,
  "message": "删除成功",
  "data": null
}
```

#### 业务规则

- 普通用户只能删除自己的评价。
- 管理员可以删除任意评价，用于处理不合适的内容。
- 删除成功后重新计算菜品评分统计，清除菜品详情缓存；无评价时平均评分写为 `0.0`，评价数量写为 `0`。
- 根据最新统计同步热门榜：菜品上架时重新计算 score 并 `ZADD` 覆盖写入；菜品下架时保持 `ZREM` 状态，**不要直接对原 score 减 1**。
- 菜品已下架不影响作者或管理员删除历史评价。

#### 失败场景

| 场景 | HTTP/code |
|---|---|
| 评价不存在 | 404 |
| 普通用户删除他人评价 | 403 |
| 未登录 | 401 |

- **请求路径**：`/admin/dishes`

#### 请求体

### 6.3 修改菜品

- **请求方法**：PUT
- **请求路径**：`/admin/dishes/{id}`
- **访问权限**：管理员
- **更新方式**：全量更新，请求字段要求与新增菜品一致

#### Path 参数

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| id | number | 是 | 菜品 ID，正整数 |

#### 请求示例

```json
{
  "name": "番茄鸡蛋面",
  "canteenName": "第一食堂",
  "windowName": "3号窗口",
  "category": "面食",
  "price": 13.00,
  "description": "番茄汤底，搭配鸡蛋和青菜",
  "imageUrl": "https://example.com/noodle.jpg",
  "status": 1
}
```

#### 成功响应

```json
{
  "code": 0,
  "message": "修改成功",
  "data": null
}
```

#### 业务规则

- 修改成功后删除对应菜品详情缓存。
- 每次修改后都按最新 `status` 同步热门榜：上架时按当前统计重新 `ZADD`，下架时执行 `ZREM`；不能只依赖应用层判断状态是否发生变化。
- 菜品不存在时返回 `404`。

---

### 6.4 下架菜品

- **请求方法**：DELETE
- **请求路径**：`/admin/dishes/{id}`
- **访问权限**：管理员
- **请求体**：无

#### 成功响应

```json
{
  "code": 0,
  "message": "下架成功",
  "data": null
}
```

#### 业务规则

- 本接口执行逻辑下架，将 `status` 修改为 0，不物理删除菜品。
- 菜品原有评价继续保留。
- 下架后，公开菜品列表、热门排行和菜品详情不再返回该菜品。
- 已下架菜品不能继续接收新评价，但历史评价仍保留在“我的评价”中。
- 下架成功后清除菜品详情缓存，并从热门榜移除。
- 重复下架同一菜品时返回 `409`，提示“菜品已处于下架状态”。
- 菜品不存在时返回 `404`。

## 8. 前后端联调注意事项

1. 前端登录成功后保存 `token`，后续请求统一通过 Axios 请求拦截器添加请求头：`Authorization: Bearer ${token}`。注意 `Bearer` 后有一个英文空格。
2. 收到 `401` 时清除本地 JWT 和用户信息，并跳转至登录页。
3. 收到 `403` 时提示“没有操作权限”，不要自动退出登录。
4. 收到 `400`、`409` 时直接展示后端返回的 `message`。
5. 分页参数从 1 开始，`size` 最大为 50。
6. 金额在前端展示时统一保留两位小数。
7. 平均评分无评价时返回 `0`，前端可显示为“暂无评分”。
8. 管理员下架菜品采用逻辑删除，前端按钮文案应使用“下架”，不要使用“永久删除”。
9. 所有密码字段只用于请求，不会出现在任何响应中。
10. 开发环境如遇跨域，可通过 Vite 开发代理将 `/api` 转发到 `http://localhost:8080`。
